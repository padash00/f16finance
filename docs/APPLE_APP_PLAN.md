# Orda — нативное приложение Apple (iPhone / iPad / Mac)

**Стек:** SwiftUI multiplatform (один таргет, три платформы), Swift 6, iOS 17+ / iPadOS 17+ / macOS 14+
**Объём v1:** все 4 роли сразу
**Backend:** существующий Next.js API (`ordaops.kz`), без переписывания
**Дата плана:** 2026-08-08

---

## Часть 0. Что показал аудит репозитория

Прежде чем планировать экраны, зафиксируем реальность бэкенда. Это меняет оценки в два раза в меньшую сторону — большая часть работы уже сделана.

### 0.1. Масштаб системы

| Метрика | Значение |
|---|---|
| API routes | **342** |
| Веб-страниц в `app/(main)` | ~130 |
| Групп прав | **9** |
| Страниц в каталоге прав | **82** |
| Отдельных capabilities | **397** (120 low / 99 medium / 106 high) |
| Аддонов (продаваемых модулей) | 8 |
| Операторских API | 23 |
| Страниц платформы (суперадмин) | 10 |

### 0.2. Мобильный транспорт уже работает — новой авторизации не нужно

`lib/server/request-auth.ts` уже принимает `Authorization: Bearer <supabase_jwt>` и валидирует его прямым запросом в GoTrue. Это значит:

```
iPhone → Bearer JWT + x-organization-id → /api/admin/*     (суперадмин, владелец, сотрудник)
iPhone → Bearer JWT                     → /api/operator/*  (оператор)
```

Никаких device-токенов, никакого отдельного мобильного контура. Это **тот же** путь, которым ходит существующее Expo-приложение — он проверен в бою.

### 0.3. Операторский мост полностью готов

В `docs/iOS_API_*.md` лежит переписка с iOS-командой «Orda Control», и по факту **все 23 операторских эндпоинта реализованы**:

| Что | Эндпоинт | Методы |
|---|---|---|
| Смена | `/api/operator/shift/{current,open,close,handover,report}` | GET/POST |
| **Продажа** | `/api/operator/inventory-sales` | GET/POST |
| **Ревизия (акт)** | `/api/operator/audit` | GET/**POST** |
| Чек-листы | `/api/operator/checklist/{templates,run,run/[id],run/[id]/complete}` | GET/POST/PATCH |
| База знаний | `/api/operator/knowledge{,/confirm}` | GET/POST |
| Инциденты | `/api/operator/incidents` | GET |
| Арена | `/api/operator/arena` | GET/POST |
| Клиенты, задачи, зарплата, профиль, обзор | `/api/operator/{customers,tasks,salary,profile,overview,lead}` | GET/POST |

`/api/operator/inventory-sales` — цитата из кода: *«тонкий клиент над тем же контуром, что и десктоп: та же смена `point_shifts`, те же `point_sales`, то же ядро расчёта. Разница — только транспорт»*.

**Вывод: оператор может продавать и делать ревизию с личного iPhone уже сегодня.** Ничего на бэке для этого дописывать не надо.

### 0.4. Главная находка — доступ гейтится **четырьмя независимыми слоями**

Это самое важное для приложения. Любой экран должен пройти все четыре, и в этом порядке:

```
1. ПЕРСОНА        кто ты вообще
   resolveRequestAuthPersona: super_admin → staff → operator → customer

2. CAPABILITIES   что тебе разрешила роль (RBAC)
   lib/core/capabilities.ts — 397 прав вида `<page>.<action>`
   = права роли (role_capabilities) + персональные оверрайды (user_capability_overrides)

3. АДДОНЫ/ТАРИФ   что купила организация
   lib/core/addons.ts — shop.catalog, addon.webpos, addon.arena,
   addon.ai, addon.hr, addon.salary, addon.telegram, addon.branding
   применяется, только если organizations.features_enforced = true

4. РУБИЛЬНИК ОРГ  что выключил суперадмин для всей организации
   organization_capability_overrides — режет право у ВСЕХ в орг, включая владельца
   (кроме `.view` — он никогда не режется этим слоем)
```

Суперадмин (email в `ADMIN_EMAILS`) проходит все четыре слоя насквозь.

**Всё это уже отдаётся одним запросом:**

```http
GET /api/auth/session-role
→ {
    isSuperAdmin, isStaff, isOperator, isCustomer, persona,
    staffRole, roleLabel, displayName, operatorId, defaultPath,
    capabilities: ["income.view", "income.create", ...],   // или ["*"] для суперадмина
    orgFeatures: ["shop.catalog", "addon.ai", ...],
    featuresAllAccess: bool,
    rolePermissionOverrides: [{ path, enabled }]
  }
```

Это **единственный** источник правды для построения интерфейса. Приложение не хардкодит меню — оно строит его из этого ответа.

### 0.5. Роли динамические, а не фиксированные

`STAFF_ROLE_MATRIX` — это Proxy, который читает роли из БД (таблицы `positions` + `position_paths`) с фоллбэком на четыре системные (`owner`, `manager`, `marketer`, `other`). Владелец может создать роль «Старший кассир» с любым набором из 397 прав.

**Следствие для приложения: жёстко зашитых экранов «для менеджера» быть не может.** Интерфейс собирается из capabilities.

### 0.6. Чего на бэке действительно нет

| Пробел | Почему важно | Объём |
|---|---|---|
| **APNs** | `lib/server/push.ts` умеет только Expo Push: фильтр `/^Expo(nent)?PushToken/` и отправка на `exp.host`. Нативный APNs-токен просто отбросится. | 1–2 дня |
| **Контракты для Swift** | Нет OpenAPI/JSON-схемы → DTO придётся писать руками по 342 роутам, это источник багов. | 3–5 дней |
| **Bootstrap-эндпоинт** | Один экран сейчас = 5–15 запросов. На сотовой сети это секунды ожидания. | 2–3 дня |
| **Дельта-синк** | Нет `updated_since` / ETag → каждый pull-to-refresh тянет всё заново. | 3–4 дня |

## Часть 1. Суперадминистратор

**Кто это:** email в env `ADMIN_EMAILS` → `isAdminEmail()` → `isSuperAdmin`.
**Отличие от всех:** обходит все 4 слоя гейтинга. `capabilities = ["*"]`. Единственная роль, работающая **между** организациями.

### Что должно быть в приложении

**Вкладка «Платформа»** (только у него, остальные её не видят вообще)

| Экран | Источник | Что делает |
|---|---|---|
| Обзор платформы | `/api/admin/platform` | MRR, число орг, активные подписки, аномалии |
| Организации | `/api/admin/organizations` | Список, поиск, создание, слаг/поддомен, логотип |
| Карточка организации | `/api/admin/organizations/capabilities` | Профиль орг + переключение аддонов + **рубильник прав** |
| Пакеты | `/api/admin/platform/packages` | Конструктор тарифов: страницы ↔ фичи ↔ capabilities |
| Биллинг и счета | `/api/admin/platform/{invoices,billing}` | Выставление, статусы оплат |
| Аналитика платформы | `/api/admin/platform/analytics` | Рост, отток, использование модулей |
| Аудит платформы | `/api/admin/platform/audit` | Кто что менял по всем орг |
| Здоровье системы | `/api/admin/health`, `/api/admin/debug/system` | Supabase, крон-задачи, ошибки |

**Плюс: полный доступ ко всему, что видят остальные три роли**, с переключателем организации в шапке (`x-organization-id`). Он должен уметь «войти как» любую орг и посмотреть её глазами владельца.

### Ключевые механики

- **Переключатель организации** — не в настройках, а в постоянно доступном месте (на Mac — в тулбаре, на iPhone — свайп в шапке). Меняет `x-organization-id` во всех последующих запросах.
- **Рубильник capability по организации** — экран со всеми 397 правами, сгруппированными по 9 разделам, с выключателями. Права с `severity: high` (их 106) выделены красным.
- **Режим наблюдателя** — визуально отличающийся интерфейс (цветная полоса сверху), когда суперадмин смотрит чужую орг. Чтобы не спутать со своей.

## Часть 2. Владелец бизнеса (подписчик)

**Кто это:** `staff.role === 'owner'`. Тот, кто платит за подписку.
**Что видит:** весь свой tenant, кроме системного администрирования. Ограничен аддонами, которые купил.

### Навигация приложения

Строится из `lib/nav/sections.tsx` → `buildOwnerNavSections()`, фильтруется по `orgFeatures`:

| Раздел | Ключевые экраны | Гейт по аддону |
|---|---|---|
| **Центр управления** | Дашборд, AI-разбор, AI-прогноз, Бизнес-аналитика, AI-финдиректор, Цели, Отчёты, Недельный отчёт, Cash Flow, ОПиУ/EBITDA, Оценка бизнеса, Финмодель точки, Налоги | AI-экраны → `addon.ai` |
| **Деньги** | Доходы, Расходы, AI-разбор расходов, **Ожидают одобрения**, Доверенные поставщики, Категории | — |
| **Магазин** | Склад, Техкарты, Документы (приёмка/списания/ревизия), Заявки, План закупа, Поставщики, Аналитика, Касса, Клиенты, Реквизиты ККМ | `shop.catalog` |
| **Команда и зарплаты** | AI-разбор команды, Зарплата, Правила ЗП, Долги точек, Операторы, Структура, Сотрудники, Кадры, Доступы | `addon.hr`, `addon.salary` |
| **Операционка** | Симуляция выручки, Задачи, Смены, Отчёты смен, Инциденты, Дни рождения, Точки и устройства | — |
| **Команда (соц.)** | Лента, Чат, Личные сообщения, Календарь, Модерация, Аналитика операторов, Эффективность (PI), Рейтинг, Достижения | — |
| **Настройки** | Настройки системы, Права и пароли, Подписка | — |

Владелец **не видит**: логи, диагностику, `/platform`, системные настройки уровня платформы.

### Что критично именно на телефоне

Владелец — не оператор. Он не сидит в приложении по 8 часов, он заходит на 40 секунд по дороге. Поэтому главный экран решает всё:

1. **Выручка сегодня** — крупно, с трендом к вчера/неделе назад, разбивка по точкам.
2. **Что требует меня** — расходы на одобрение (`/expenses/pending`), заявки склада, просроченные долги, инциденты. Всё с действием прямо из карточки.
3. **Что сломалось** — точка не открыла смену, нулевые остатки, аномалия в расходах.
4. **AI-сводка дня** — уже есть `/api/cron/morning-ai-insight`, просто показать.

Одобрение расхода должно работать **из пуш-уведомления, не открывая приложение** (см. часть 7).

### Мультиорганизационность

Владелец может владеть несколькими организациями. Переключатель — тот же механизм `x-organization-id`, но UI мягче, чем у суперадмина: просто селектор в профиле.

## Часть 3. Сотрудники (по выданным правам)

**Кто это:** запись в `staff` с ролью, отличной от `owner`. Роль **любая** — системная (`manager`, `marketer`) или созданная владельцем в `/access`.

### Это самая сложная часть, и вот почему

Нельзя нарисовать «экран менеджера». Роль «Бухгалтер» может иметь права только на `income.*` + `expenses.*` + `tax.*`. Роль «Старший кассир» — `store-revisions.*` + `pos.*` + `shifts.view`. Владелец придумает их сам.

**Значит, интерфейс должен собираться во время выполнения.**

### Как строится интерфейс

```
1. Логин → GET /api/auth/session-role
2. Получили capabilities: ["income.view","income.create","expenses.view",...]
3. Прогоняем каталог из lib/core/capabilities.ts (портирован в Swift):
     страница видна, если есть ЛЮБОЕ право этой страницы
     кнопка видна, если есть КОНКРЕТНОЕ право (income.create)
4. Вычитаем rolePermissionOverrides (path + enabled:false)
5. Вычитаем то, чего нет в orgFeatures (если !featuresAllAccess)
6. Собираем разделы, выкидываем пустые
7. Если разделов 0 → экран «Обратитесь к владельцу»
8. Если раздел 1 → приложение открывается сразу в него, без таб-бара
```

### Правило для каждого элемента

| Элемент | Право |
|---|---|
| Раздел в меню | любое право из группы |
| Экран | `<page>.view` |
| Кнопка «Добавить» | `<page>.create` |
| Свайп «Изменить» | `<page>.edit` |
| Свайп «Удалить» | `<page>.delete` |
| Кнопка «Экспорт» | `<page>.export` |
| Одобрить расход | `expenses-pending.approve` |
| Провести ревизию | `store-revisions.commit` |
| Выплатить зарплату | `salary.create_payment` |

**Права с `severity: high` (106 штук) требуют подтверждения жестом или Face ID** — «Очистить весь склад», «Удалить весь каталог», «Выгрузить логины и пароли», «Списать долг».

### Обязательное правило безопасности

Скрытая кнопка ≠ защита. Сервер всё равно проверяет через `requireCapability()`. Приложение должно корректно обрабатывать `403 forbidden` — показывать понятное «У вас нет права X, попросите владельца», а не «Ошибка 403».

## Часть 4. Операторы

**Кто это:** `operator_auth` + `operators`. Работает смену на точке. Продаёт, считает, закрывает кассу.
**Отличие:** отдельный контур `/api/operator/*`, никаких `/api/admin/*`.

### Это не «урезанный владелец» — это другое приложение

Оператор держит телефон одной рукой, часто с товаром в другой, часто в полутьме, часто в спешке при очереди. Интерфейс должен быть **крупным, однорукимиспользуемым и работать без интернета**.

### Экраны

**Главный — «Смена»** (всё остальное вторично)

| Состояние | Что показываем |
|---|---|
| Смена закрыта | Огромная кнопка «Открыть смену» + поле старта кассы + предупреждение, если оператора нет в графике на сегодня |
| Смена открыта | Выручка смены (растёт вживую), время с открытия, число чеков, кнопка «Продать», текущие чек-листы |
| Пора закрывать | Форма закрытия: наличные, Kaspi, для ночной — Kaspi до/после полуночи; блокировка, если есть незавершённый обязательный чек-лист |
| Передача смены | Выбор сменщика + заметки + передаваемая касса |

`/api/operator/shift/*` — всё готово. Открытие проверяет график: нет в расписании → блок.

**Продажа** — `/api/operator/inventory-sales`

- Сканер штрихкода камерой (VisionKit, непрерывный режим — сканируешь товар за товаром, не закрывая камеру)
- Каталог витрины с поиском и крупными карточками
- Корзина, количество, скидка
- Оплата: наличные / Kaspi / смешанная
- Привязка клиента + списание бонусов (`/api/operator/customers`)
- Чек: QR на публичную страницу `/r/<saleId>` — клиент сканирует, чек у него в телефоне
- **Офлайн-очередь**: продажа записывается локально с `local_ref`, уходит на сервер при появлении сети. Поле `local_ref` в контракте уже есть — сервер к этому готов.

**Ревизия** — `/api/operator/audit` (GET снимок + POST подсчёт)

- Режим непрерывного сканирования: навёл → товар определился → ввёл количество → следующий
- Черновик переживает перезапуск приложения и смену устройства (серверный черновик уже реализован в вебе — `/api/admin/store/revisions/draft`)
- Расхождения подсвечиваются сразу: ожидали 12, насчитал 9 → минус 3, красным
- Итог: сколько позиций сошлось, сколько нет, на какую сумму

**Остальное**

| Экран | Эндпоинт |
|---|---|
| Мои задачи | `/api/operator/tasks` |
| Чек-листы смены (с фото-подтверждением) | `/api/operator/checklist/*` |
| База знаний + подтверждение прочтения | `/api/operator/knowledge{,/confirm}` |
| Моя зарплата (неделя, смены, бонусы, штрафы) | `/api/operator/salary` |
| Мои смены и график | `/api/operator/shifts` |
| Инциденты по мне | `/api/operator/incidents` |
| Арена: станции, продление сессий, тех-лог | `/api/operator/arena` |
| Достижения и рейтинг | `/api/operator/overview` |
| Профиль | `/api/operator/profile` |

### Офлайн — не опция, а требование

Точка может быть в подвале. Продажа не должна зависеть от связи.

```
Локальная база (SwiftData):
  ├── каталог витрины      — синк при открытии смены
  ├── очередь продаж       — local_ref, отправка при сети
  ├── черновик ревизии     — merge с серверным
  └── чек-листы + фото     — отложенная загрузка
```

### Почему логика вынесена в OrdaKit

Расчёт доступа (4 слоя × 397 прав) — самая ошибкоопасная часть. Она должна быть покрыта тестами и не зависеть от UI. Тест-кейс на каждую роль: «сотрудник с правами X видит ровно экраны Y».

### Синхронизация каталога прав с вебом

397 прав живут в `lib/core/capabilities.ts`. Если их править в двух местах — разъедутся. Решение:

```bash
# scripts/export-capabilities.mjs (написать) → capabilities.json
# → Swift-генератор в build phase → CapabilityCatalog.swift
```

CI падает, если каталоги разошлись.

## Часть 6. iPhone / iPad / Mac — оптимизация с первого дня

Не «сначала iPhone, потом растянем». Каждый экран проектируется в трёх раскладках сразу.

### Каркас навигации

`NavigationSplitView` — единственный контейнер, который сам адаптируется:

```
iPhone            iPad портрет        iPad ландшафт / Mac
┌──────────┐      ┌───┬─────────┐     ┌────┬──────┬─────────┐
│          │      │ ▤ │         │     │    │      │         │
│  Экран   │      │ся-│  Экран  │     │сай-│список│ детали  │
│          │      │дбар│        │     │дбар│      │         │
├──────────┤      │(вы-│        │     │    │      │         │
│ ▣ ▣ ▣ ▣  │      │дви-│        │     │    │      │         │
└──────────┘      │жной│        │     └────┴──────┴─────────┘
 таб-бар          └───┴─────────┘      три колонки
```

| | iPhone | iPad | Mac |
|---|---|---|---|
| Навигация | Таб-бар (5 вкладок) | Боковая панель, 2–3 колонки | Боковая панель + тулбар + меню-бар |
| Списки | `List`, карточки | `Table` с сортировкой по колонкам | `Table` + контекстные меню |
| Формы | Полноэкранные `sheet` | `sheet` по центру / инспектор справа | Отдельное окно |
| Графики | Свайп по периодам | Крупные, несколько рядом | Наведение курсора → тултип |
| Ввод | Тач + Face ID | Тач + Apple Pencil + клавиатура | Клавиатура + мышь |

### Что даёт iPad конкретно

- **Ревизия вдвоём**: iPad лежит на складе как «пульт» — список позиций слева, счёт справа. Один сканирует iPhone, второй видит на iPad.
- **Split View**: план закупа рядом с остатками, одновременно.
- **Несколько окон**: перетащил вторую точку во второе окно, сравниваешь.
- **Apple Pencil**: подпись на акте ревизии и приёмке — юридически осмысленно.
- **Внешняя клавиатура**: ⌘F поиск, ⌘N новая запись, ⌘↩ сохранить.

### Что даёт Mac конкретно

Владелец и бухгалтер большую часть работы делают за компьютером. Mac-версия — не бонус, а основной инструмент для них.

- **Меню-бар**: пункт в строке меню macOS с выручкой в реальном времени, без открытия приложения.
- **Полное меню приложения**: Файл → Экспорт в Excel, Правка, Вид, Окно.
- **Горячие клавиши на всё**: ⌘1..⌘9 — разделы, ⌘R — обновить, ⌘E — экспорт, пробел — Quick Look карточки.
- **Множественные окна**: дашборд на одном мониторе, склад на другом.
- **Перетаскивание**: накладная PDF из Finder → окно приёмки → AI-распознавание (`/api/admin/store/receipts/ai-parse` уже есть).
- **Печать**: ценники, акты, отчёты — через нативный диалог печати.

### Реализация

Один SwiftUI-код + точечные различия:

```swift
@Environment(\.horizontalSizeClass) private var sizeClass

var body: some View {
    if sizeClass == .compact { CompactLayout() } else { RegularLayout() }
}

#if os(macOS)
.commands { OrdaCommands() }   // меню-бар и горячие клавиши
#endif
```

Ожидаемое переиспользование кода: **~85%**. Различаются каркас навигации, плотность списков и жесты.

## Часть 7. Функции Apple, которые дают реальную пользу

Не «фишки ради фишек» — каждая закрывает конкретную боль.

### Live Activity + Dynamic Island — главная функция для оператора

Смена открыта → на экране блокировки живёт карточка:

```
┌────────────────────────────────────┐
│  ● Смена открыта   ·  4 ч 12 мин   │
│  Выручка   184 500 ₸       ↑ 23 %  │
│  Чеков 47   ·   Наличные 92 300 ₸  │
│           [Продать]  [Закрыть]     │
└────────────────────────────────────┘
```

В Dynamic Island — свёрнутая выручка, всегда на виду. Оператор не открывает приложение, чтобы посмотреть, как идёт смена. Обновление через APNs push-to-start.

### Виджеты (WidgetKit)

| Виджет | Кому | Размер |
|---|---|---|
| Выручка сегодня по точкам | владелец | средний |
| Требует внимания (N расходов, M заявок) | владелец, сотрудник | малый |
| Моя смена / моя зарплата за неделю | оператор | малый |
| Низкие остатки | сотрудник склада | средний |
| График смен на неделю | оператор | большой |

На Mac виджеты живут в Центре уведомлений, на iPad — на главном экране, в StandBy на iPhone — на тумбочке ночью.

### Действия прямо из уведомления

Пуш «Оператор Иван подал расход 45 000 ₸ без чека» → долгое нажатие → **[Одобрить] [Отклонить] [Посмотреть]**. Одобрение уходит на `/api/admin/expenses/[id]/approve` без открытия приложения. Для владельца это экономит десятки открытий в день.

### Камера (VisionKit)

- **Непрерывное сканирование штрихкодов** — `DataScannerViewController`. Не «сфотографировал → распознал → закрыл», а поток: держишь камеру, товары падают в список. Для ревизии на 800 позиций это разница между 3 часами и 40 минутами.
- **Сканер документов** — накладная поставщика фотографируется и уходит в существующий AI-парсер.
- **Live Text** — выделить номер накладной прямо с фото.

### Siri и быстрые команды (App Intents)

```
«Сири, какая выручка сегодня»
«Сири, открой смену»
«Сири, сколько расходов ждут одобрения»
```

Плюс автоматизации: «Каждый день в 9:00 показать сводку», «Когда прихожу на точку — открыть смену».

### Остальное

| Функция | Польза |
|---|---|
| **Face ID / Touch ID** | Замок приложения + подтверждение опасных действий (106 прав уровня high) |
| **Handoff** | Начал смотреть отчёт на iPhone → открыл Mac → он уже там |
| **Spotlight** | Поиск товара, оператора, клиента из системного поиска |
| **Swift Charts** | Нативные графики вместо картинок с сервера — с наведением, зумом, анимацией |
| **ShareLink** | Отчёт PDF (`/api/admin/reports/pdf` есть) → в Telegram/почту в два тапа |
| **Wallet (PassKit)** | Карта лояльности клиента — в репо уже есть Google Wallet, добавить Apple |
| **Управление в Пункте управления** | «Открыть смену» кнопкой из шторки |
| **Фокусирование** | Режим «Смена» — только рабочие уведомления |
| **Sensory feedback** | Тактильный отклик: успешное сканирование ≠ ошибка сканирования |

## Часть 8. Вход в приложение и анимации

Просили «когда заходить какая-то анимация». Вот сценарий.

### Последовательность запуска

```
0.0 с  Launch screen — статичный логотип на фоне #070809
0.2 с  Логотип оживает: знак собирается из частей, лёгкое свечение
0.4 с  Фон: живой mesh-градиент (iOS 18 MeshGradient), медленное дыхание
0.6 с  Face ID — если включён замок
0.9 с  Логотип поднимается вверх и уменьшается → становится шапкой
1.1 с  Контент проявляется каскадом: карточки въезжают снизу
       со сдвигом 40 мс друг за другом, spring(0.5, 0.8)
1.4 с  Цифры «прокручиваются» до значений (ContentTransition.numericText)
```

Итого меньше полутора секунд до полезного контента. Ничего не «висит» — анимация играет **поверх** уже идущей загрузки данных.

### Появление роли

После `session-role` интерфейс собирается с характером роли:

| Роль | Акцент | Первый экран |
|---|---|---|
| Суперадмин | холодный фиолетовый, плотная сетка | Платформа |
| Владелец | изумрудный, крупные метрики | Деньги сегодня |
| Сотрудник | нейтральный, только его разделы | Его главный раздел |
| Оператор | тёплый янтарный, огромные элементы | Смена |

### Язык движения

| Где | Что |
|---|---|
| Переход в карточку | `NavigationTransition.zoom` (iOS 18) — карточка разворачивается в экран, а не подменяется |
| Между вкладками | `matchedGeometryEffect` на общих элементах |
| Числа | Прокрутка разрядов, не подмена текста |
| Загрузка | Скелетоны с бегущим бликом, не спиннер |
| Иконки | `SF Symbol` эффекты: `.bounce` на успех, `.pulse` на ожидании |
| Списки | Появление с задержкой 30–40 мс между строками, максимум для 12 первых |
| Обновление | Pull-to-refresh с тактильным откликом в момент срабатывания |
| Ошибка | Короткая горизонтальная тряска + `.error` haptic |
| Продажа проведена | Чек «улетает» вверх + `.success` haptic + звук |
| Смена закрыта | Полноэкранная сводка с последовательным появлением цифр |

**Правило:** анимация никогда не задерживает действие. Максимум 300 мс на переход, 150 мс на отклик элемента. Всё уважает «Уменьшение движения» в настройках доступности.

## Часть 9. Работы на бэкенде

Немного, и все — расширения, не переделки.

### Обязательное

**1. APNs** (1–2 дня)

`lib/server/push.ts` сейчас:
```typescript
const valid = tokens.filter((t) => /^Expo(nent)?PushToken/.test(t))  // нативный токен отброшен
await fetch('https://exp.host/--/api/v2/push/send', ...)
```

Нужно: определять тип токена по `mobile_push_tokens.platform` и ветвить — Expo Push или APNs (`node-apn` / HTTP/2 к `api.push.apple.com`). Таблица уже есть, колонка `platform` уже есть. Плюс `/api/mobile/register-push` должен принимать APNs-токены (сейчас жёстко проверяет префикс `ExponentPushToken`).

Дополнительно для Live Activity: приём `push-to-start` токенов и отправка обновлений активности.

**2. Экспорт каталога прав** (1 день)

`scripts/export-capabilities.mjs` → `capabilities.json` → генератор Swift. Чтобы 397 прав не расходились между вебом и приложением.

### Желательное (сильно улучшает ощущение)

**3. Bootstrap-эндпоинт** (2–3 дня)

`GET /api/mobile/bootstrap` — один ответ: сессия + права + аддоны + сводка главного экрана + счётчики бейджей. Сейчас это 5–15 запросов. На LTE разница ощутимая.

**4. Дельта-синхронизация** (3–4 дня)

`?updated_since=<iso>` на списочных эндпоинтах (каталог, операторы, клиенты, задачи) + `ETag` / `If-None-Match`. Каталог на 3000 позиций не должен качаться целиком при каждом обновлении.

**5. Идемпотентность продаж** (0.5 дня)

`local_ref` в контракте продажи уже есть — проверить, что сервер по нему дедуплицирует. Критично для офлайн-очереди: сеть пропала после отправки, но до ответа → повтор не должен создать второй чек.

## Часть 11. Риски

| Риск | Почему реален | Что делаем |
|---|---|---|
| **397 прав разъедутся между вебом и приложением** | Владелец добавит право в вебе, приложение о нём не узнает и покажет кнопку, которую сервер отвергнет | Генерация каталога из одного источника + падение CI при расхождении |
| **Офлайн-продажи создадут дубли чеков** | Сеть отвалилась после отправки, до ответа | Идемпотентность по `local_ref` на сервере, проверить до этапа 1 |
| **Экран владельца собирает 15 запросов** | Веб-API дробный, на LTE это 3–5 секунд | Bootstrap-эндпоинт + агрессивный кэш SwiftData |
| **App Review отклонит** | Приложение только для сотрудников, нет публичной регистрации | Демо-аккаунт в заявке, честное описание B2B-назначения. При отказе — Apple Business Manager / кастомная дистрибуция |
| **Mac-версия окажется «айпадом на мониторе»** | Ленивый Catalyst без адаптации | Меню-бар, горячие клавиши и `Table` — в определении готовности этапа 6, не «если успеем» |
| **Паритет со 130 страницами веба недостижим** | Часть страниц (печать, embed, конструкторы) телефону не нужна | Явно зафиксировать: 100% паритет по данным, ~70% по экранам. Остальное — открытие веб-версии внутри приложения |
