# Файлы в хранилище: кто вправе писать

Коротко: **никто, кроме сервера.** Браузер, приложение и киоск в Supabase Storage не пишут — они просят разрешение у нашего API, а тот выдаёт одноразовую ссылку.

## Как устроено

| Кусок | Где | Что делает |
|---|---|---|
| `lib/server/storage-upload.ts` | сервер | политики корзин: разрешённые типы, предельный размер, кто куда кладёт |
| `app/api/admin/storage/upload-url/route.ts` | сервер | проверяет право, тип и размер → выдаёт одноразовую ссылку |
| `lib/client/upload-file.ts` | браузер | просит ссылку, кладёт файл обычным PUT |
| `verifyUploadedObject()` | сервер | смотрит, что реально легло по адресу, и убирает, если не подошло |

Через сервер целиком файлы гнать нельзя: Vercel не пропускает тело больше ~4,5 МБ, а рекламный ролик на витрину весит сотню. Отсюда разделение — решение принимает сервер, байты идут мимо него.

Проверка `npm run audit:app` (скрипт `audit-browser-db.mjs`) роняет сборку, если в браузерном коде снова появится прямая запись в хранилище.

## Состояние политик (20 августа 2026)

На `storage.objects` должны остаться **только** политики на чтение:

```
customer_display_ads_read                    SELECT  public
product_photos_read                          SELECT  public
help-images public read                      SELECT  public
org-logos public read                        SELECT  public
inventory-attachments-select-authenticated   SELECT  authenticated
```

Все восемь корзин публичны, поэтому чтение и без политик работает — эти строки ни на что не влияют и оставлены как есть.

Записи в списке быть не должно ни одной. Сервер пишет сервисным ключом, а он RLS не касается.

Проверить:

```sql
select policyname, cmd, roles
from pg_policies
where schemaname = 'storage' and tablename = 'objects'
order by policyname;
```

## Что было и почему это важно

Политики раздавали право записи широко:

- **`Give users access to own folder`** — название про свою папку, условие — просто «залогинен», без ограничения по папке и корзине, `cmd: ALL`. Любой вошедший мог читать, перезаписывать и удалять любой файл в любой корзине: документы операторов, чеки расходов, вложения чатов — всех арендаторов сразу.
- **`customer_display_ads_write` / `_delete`, `product_photos_write` / `_delete`, `team_chat_attachments_write`** — выданы роли `public`. В Postgres `public` — это все роли, включая невошедших. Публичный ключ Supabase лежит в коде сайта и приложения, то есть посторонний мог стереть все фото товаров и всю рекламу на витринах.
- **`Allow authenticated uploads` / `delete`** — чеки расходов: запись и удаление любому вошедшему, через границы арендаторов.

Они держались на том, что браузер грузил файлы сам. Как только загрузки переехали на подписанные ссылки, политики стали не нужны — и были сняты.

## Второй пояс — на самой корзине

Ограничения стоят и на корзинах, до всяких политик и до нашего кода:

| Корзина | Предел | Типы |
|---|---|---|
| `customer-display-ads` | 200 МБ | JPEG, PNG, WEBP, GIF, MP4, WEBM, MOV |
| `operator-files` | 20 МБ | JPEG, PNG, WEBP, HEIC, PDF |

Хранилище не примет ни файл сверх предела, ни тип не из списка — даже если разрешение уже выдано.

## Если что-то перестало загружаться

Не возвращайте всеобщую политику. Скажите, какое именно действие сломалось, — либо в `STORAGE_POLICIES` не хватает записи под эту задачу, либо роут пишет не сервисным ключом. Оба случая чинятся в коде.

# Таблицы: кто что видит напрямую

Та же проверка, что и по файлам, но по базе. RLS включён на **всех** таблицах `public` — здесь фундамент изначально верный, в отличие от хранилища.

## Что было снято (20 августа 2026)

| Таблица | Политика | Что разрешала |
|---|---|---|
| `operator_auth` | `Authenticated users can insert/update/delete` | любому вошедшему — переписать чужой логин и пароль или удалить учётку оператора |
| `operator_chat_messages` | `Allow all for authenticated` | любому вошедшему — читать, править и удалять чужую переписку, без разделения по организациям |
| `operator_chats` | `Users can create chats` | любому вошедшему — создавать чаты |
| `direct_message_blocks` | `dm_blocks_all` (`qual: true`) | вообще любому, без входа — ставить и снимать блокировки личных сообщений |

Все четыре держались на предположении, что в базу ходит клиент. Он не ходит: сервер работает сервисным ключом мимо RLS, браузер — только в наши роуты (`audit-browser-db.mjs` это стережёт).

Живая подписка (`postgres_changes`) идёт на другие таблицы — задачи, расходы, доходы, склад, смены. Их политики не трогали.

## Что осталось открытым и почему

Читаются публичным ключом без входа: `kz_holidays`, `help_images`, `payment_providers`, `payment_provider_products`, `position_paths`. Тенантных данных в них нет — это справочники, одинаковые для всех клиентов.

Остальное закрыто одним из трёх способов: скоуп по организации (`can_access_organization`), сверка с `auth.uid()` или «только сервисный ключ».

## Как проверить, что не расползлось

```sql
-- Таблицы без RLS: должно быть пусто.
select tablename from pg_tables where schemaname = 'public' and not rowsecurity;

-- Политики, доступные роли public: у каждой должно быть условие —
-- скоуп организации, auth.uid() или service_role. `true` и
-- `auth.role() = 'authenticated'` без иного условия — это «всем».
select tablename, policyname, cmd, qual, with_check
from pg_policies
where schemaname = 'public' and 'public' = any(roles)
order by tablename;
```

Роль `public` в Postgres — это все роли разом, включая невошедших. Не «публичный раздел».
